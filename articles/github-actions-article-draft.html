GitHub Actionsで記事作成を自動化する前に確認すること

GitHub ActionsとGitHub Copilotを使い、確認済みのIssueから記事下書きを作る流れを安全に運用するための確認項目を整理します。

自動化の範囲を下書きまでにする

GitHub Actionsを使うと、リポジトリ上の決まった操作をきっかけに処理を実行できます。 AIを使って記事を作る場合でも、最初から公開までを自動化するのではなく、 まずは下書きPull Requestの作成までにとどめる運用が考えられます。

確認済みIssue
記事下書き作成
Pull Request確認
人が公開判断

下書きができた段階で人が内容を確認すれば、生成された文章をそのまま公開せずに済みます。 自動化の便利さと、公開前の確認を分けて設計することが重要です。

この記事の位置づけ
この記事は、GitHub ActionsとGitHub Copilotを使った記事下書き作成の設定確認を目的に、 公開前に見直したい運用上の項目をまとめたものです。

最初に確認したい3つの項目

1. トリガー 記事作成を開始するラベルを、意図せず付けない運用になっているか確認します。
2. 変更内容 Pull Requestに含まれる記事の差分を、人が確認できる状態になっているか見ます。
3. 公開前確認 事実関係と広告表記を、公開前に見直す手順が用意されているか確認します。

この3点は、ワークフローが正常に実行されるかだけでなく、生成された記事を公開するまでの流れに関わります。 設定が動作していても、確認の役割やタイミングが曖昧なままでは、意図しない内容が公開される可能性があります。

ラベルをトリガーにするときの注意

記事作成の開始条件としてラベルを使う場合は、対象のラベルを誤って付けないことが大切です。 付与する人やタイミングを決め、確認前のIssueに開始用ラベルを付けないようにします。

  • 記事の入力内容を確認してから、開始用ラベルを付ける
  • 似た名前のラベルと取り違えない
  • 意図しないIssueが処理対象になっていないか確認する
ラベル付与は公開許可そのものではありません。
ラベルをきっかけに下書きを作成できても、記事の公開判断はPull Request上で別に行います。

Pull Requestの変更内容を確認する

自動作成されたPull Requestでは、追加されたファイルと本文の差分を確認します。 見出しや段落が意図した内容になっているか、Issueにない情報が加えられていないかを読み合わせます。

記事ファイルだけが変更対象になっているかも確認したい項目です。 下書き作成の目的と関係ないファイルに変更が含まれている場合は、その理由を確認してから判断します。

公開前に事実関係と広告表記を確認する

記事を公開する前に、書かれている事実関係を確認します。 自動生成された文章であっても、内容が正しいことを自動的に保証するものではありません。

広告やアフィリエイトリンクを含む場合は、読者が広告だと分かる表記になっているかも確認します。 リンクの有無や表示内容を、記事の差分とあわせて見直します。

確認を終えてから公開する
この記事の流れでは、Issueの確認、下書きPull Requestの確認、事実関係と広告表記の確認を経てから、 人がPull Requestをマージします。

まとめ

GitHub ActionsとGitHub Copilotを使えば、確認済みのIssueをもとに記事下書きを作る流れを組み立てられます。 ただし、最初は公開までを自動化せず、下書きPull Requestの作成までに範囲を限定するほうが確認しやすくなります。

運用時は、トリガーとなるラベル、Pull Requestの変更内容、公開前の事実関係と広告表記を順番に確認します。 このIssueは設定確認用のため、記事として公開する場合も内容を見直してからPull Requestをマージします。
